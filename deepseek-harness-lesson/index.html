DeepSeek Harness 学习手册

不是从 40 多个包名开始背，而是沿一条因果链理解：Cordis 怎样承载插件，Harness 怎样定义能力，Profile 怎样启动应用，Preset 怎样组合 Agent，最后一条消息怎样变成可恢复的执行记录。

核查日期：2026-09-17 · 核查版本：master @ 0d1f500 · 预计阅读：35–50 分钟

一句总纲DeepSeek Harness 是一棵由 Profile 在启动时组装的 Cordis 插件树；它用 capability seam 替换实现，用 preset 组合每种 Agent，用 Session 日志保存事实，再由 live Agent 驱动 Turn 与 Step。
读者假设懂进程、对象、接口和配置文件即可；不要求了解 Cordis、事件溯源或 Agent Loop。文中伪代码只表达关系，不对应真实 API 语法。

02 · 学习地图：从底座到一次执行

用户表面：Web / CLI / SDK / ACP
运行时：Session → live Agent → Turn → Step
Agent 组合：Preset → Scope / Isolate
应用组合：Profile → Bundles + Patches → App Boot
Harness 领域：LLM / Tools / Session / FS / Shell / Subagent seams
Cordis 底座：Plugin / Context / Service / Fiber / Event / Effect / Loader

向下是依赖：上层使用下层机制；向上是产品化：底层原语被逐步组合成用户可见的 Agent 应用。Seam 横跨 Harness 能力包，不是夹在两层之间运行的对象。

贯穿场景：用户启动 Web Profile，新建 Session S1 并选择 PTC，然后发送“列出当前目录并解释项目结构”。后面每章都回答这条路径上新增的一个问题。

03 · 底座 Cordis：让所有东西都成为插件

先讲人话：Cordis 提供一个可插拔、可等待依赖、可撤销安装的运行环境。它不知道什么是 Agent；它只知道插件如何贡献能力，以及卸载时如何完整收回。

场景问题：模型、工具、存储和 Agent Loop 互相依赖。如果把它们写死在一个启动函数里，更换 Provider、局部重载和失败清理都会牵一发动全身。

Plugin

一块可以装上和卸下的功能。

准确机制：函数插件或 Service 子类由 Cordis 挂载；模型适配器、工具中心、Session 日志和 Agent Loop 在 DSH 中全都是插件。

误解：Plugin 不等于 npm package；一个 package 可以导出多个插件。

Context

插件进入系统后拿到的运行环境入口。

准确机制：它是代理对象，负责服务解析、事件注册、effect 归属及派生 Context；普通属性读取会进入 Cordis 的服务解析器。

误解：它不是把所有服务复制进去的普通字典。

Fiber

某个插件“这一次运行”的生命周期记录。

准确机制：Fiber 持有插件上下文、依赖状态和 disposables；插件重载或卸载时，相关注册按生命周期撤销。

例子：LLM Provider 的 Fiber 卸载后，它提供的实现随之消失。

Effect

安装动作必须附带拆除动作。

准确机制：工具、提示词、监听器和服务注册都应是 reversible effect；Fiber teardown 触发 disposer。

误解：不是“最后有空再清理”，而是注册协议的一部分。

Service 与 inject

消费者按能力名字找服务，不直接 import 某个实现。

准确机制：Provider 提供稳定的 ctx.<key>；声明了 inject 的插件会等待必需服务可用再激活。

结果：启动顺序来自依赖，而不是手写先后。

Typed Event

插件之间通过约定好的事件扩展流程。

准确机制：Cordis 支持 emit、waterfall、parallel、serial、bail；事件模式决定等待、顺序和返回值语义。

误解：waterfall 监听器若不调用 next，会主动截断后续链。

04 · Harness 与 Capability Seam：把 Agent 领域放上去

先讲人话：Cordis 给了插座和装卸机制；Harness 决定需要哪些插座，例如 LLM、Shell、FS、Session 和 Tools，以及谁提供、谁使用。

ctx.llmctx.sessionsctx.agentsctx.toolsctx.fsctx.shellctx.terminalsctx.subagents

一条 seam 必须有三个角色

例 1 · LLM

Definition消息、流和 adapter registry

ProviderDeepSeek、Replay 等 adapter

ConsumerAgent Loop 准备并派发模型请求

例 2 · Shell

DefinitionShell 执行请求与结果

ProviderLocal/Sandbox/SSH executor

Consumerbash/pwsh 工具和 Terminal backend

例 3 · Persistence

Definitioncreate/open/stat/list/export

ProviderJSONL persistence

ConsumerAgent Loop 创建与恢复 Session

设计收益：把 FS、Subprocess、Sandbox 指向远程执行世界时，Bash、PTY 和 LSP 可以沿 seam 一起迁移，而消费者无需各写一套远程分支。

05 · Bundle、Profile、App Boot：应用不是硬编码出来的

先讲人话：Bundle 是可复用配置块，Profile 是“这次启动要叠哪些块”，App Boot 把最终配置真正挂成 Cordis 插件树。

Bundle

一包可组合的 Cordis 配置行。

例子：dsh-base 放公共底座；web-app、headless、sdk-app、acp-app 添加不同应用表面。

不是：运行时服务容器。

Profile

一个命名的完整启动选择。

它列出有序 Bundles，持有自己的 patch，并接受 home patch 与命令行 overlay。

例子：web、headless、sdk、sdk-minimal、acp。

App Boot

把配置材料变成正在运行的应用。

它加载环境、解析 Profile、叠加 patch、准备模块解析、挂载插件并审计 required entries。

边界：Profile 决定整个进程是什么应用；Preset 决定某个 Session 使用什么 Agent 配方。两者名字相似，但作用范围完全不同。

06 · Session 与 Agent：记录和执行不是同一个东西

先讲人话：Session 是可以留下来的对话事实；Agent 是当前内存里负责把这段对话继续跑下去的执行者。

Session

拥有 session id、header 和 append-only event log。消息、工具调用、Turn/Step、请求信息和 preset 选择都以事实记录。

生命周期：可以跨进程重启继续存在。

live Agent

持有 inbox、状态与 driver，接收 followup/steer/inject，驱动模型和工具直到空闲。

生命周期：只在当前进程加载期间存在；resume 会在旧 Session 上重建一个新 Agent 对象。

Query

用户提交的一次输入，进入 Agent inbox。

Turn

从接纳输入到没有继续工作为止；可以包含零个或多个 Step。

Step

一次模型请求，以及该次请求产生的工具调用。

07 · Preset 与双平面：同一个 Host 上跑不同 Agent

先讲人话：Host Plane 提供整栋楼共用的基础设施；Preset 选择某类 Agent 使用的提示词、工具和可选行为。类比到这里为止：真实实现是插件树、注册层和服务 realm，不是两台机器。

平面典型内容生命周期解决的问题
Host PlaneLLM registry、ToolsService、Session persistence、FS、Shell、Sandbox、API接近进程为所有 Session 提供公共基础设施
Agent/Preset Planepersona、tool contributions、skills、compaction、plan mode、delegation每个 preset generation为一类 Agent 选择组合

Standing generation

PTC generation G1
├─ persona / tools / skills / listeners
├─ Agent A（Session S1）加入 G1
└─ Agent C（Session S3）加入 G1

PTC 配置文件变化
└─ 新建 generation G2
   └─ 后续 Agent E 加入 G2

旧 Agent 仍留在 G1，不会在对话中途换工具集。
当前配置事实：PTC 使用 host shell 与 FS，并私有化 planMode、compaction/toolResultPruner、workflowEngine 等；minimal 使用 complete persona、私有 terminals realm、persistent shell，且不安装 compaction。

08 · Scope 与 Isolate：一个管注册可见性，一个管服务实例

先遇到问题：共享 ToolsService 怎样服务不同 Preset？

ToolsService 是 Host 上的一份共享注册中心。PTC 和 minimal 都向它注册内容，但不能让所有 Agent 看见并集。

Scope

给注册内容加归属，并让查询只合并相关层。

注册：PTC Context 携带 K_ptc，bash 写入 K_ptc layer。

关联：Agent A 的 K_A 以 K_ptc 为父。

查询：ToolsService 合并 global → K_ptc → K_A。

Isolate

让同一个服务名在不同 Context 子树解析到不同实例。

路由：terminals 从 S_root_terminals 改指 S_min_terminals。

结果：minimal 组内 Provider 和 Consumer 使用私有 TerminalService。

问题机制理由
PTC 与 minimal 看见不同工具Scope共享一份 ToolsService，只过滤内部记录
minimal 使用独立 PTY registryisolate需要另一份有状态服务实例
PTC 使用不同 personaScopeSystemPrompt 是 scope-aware registry
PTC 拥有独立 compaction providerisolate是服务实现，不只是注册条目
最稳的判断句：
Scope 回答“共享注册中心应为这个 Agent 返回哪些记录？”
Isolate 回答“这个 Context 中的服务名应连接哪一个实现实例？”

09 · 一条用户消息如何跑完整个系统

先讲人话：Agent 从 inbox 接纳输入，组装当前 prompt 和工具，冻结一次模型请求；若模型调用工具，记录结果并再走一个 Step，直到没有待完成工作。

  1. 输入：followup 进入 next-turn inbox；steer 可进入当前 Turn 的后续 Step；inject 等待下一次被接纳的请求。
  2. 组装：SystemPrompt 按 Agent scope 合并 sections，Tools 按 scope 生成 wire schemas，Session 投影提供模型历史。
  3. 拦截：agent/pre-step 可以拒绝或改写输入；agent/request 与 LLM adapter 完成实际路由。
  4. 请求：准备好的 adapter 冻结请求并 stream；可见文本最终结算为 durable assistant event。
  5. 工具：模型工具调用经过 pre-execute → execute → post-execute，call/result 成对进入 Session。
  6. 继续：有工具债务或 next-step 输入就开始新 Step；否则经过 turn-stopping 后结束 Turn。

10 · Session Log、Projection 与恢复

先讲人话：系统不只保存最后一屏消息，而是保存发生过的关键事实；当前状态是从这些事实折叠出来的。

Append-only Event Log

保存 turn/start、step/start、user/message、request/header、assistant/message、tool/call、tool/result 等事实。

价值：恢复、fork、transcript、telemetry 和诊断共享同一事实来源。

Projection

把事件按顺序 fold 成当前状态，例如 inbox、Turn 边界、当前 preset 或 UI 所需视图。

边界：Projection 是派生状态，不取代原始日志。

事件事实
  session/create
  agent-preset/selected = ptc
  turn/start
  user/message
  request/header
  assistant/message
  turn/end
       │
       ├─ deriveMessages → 下次模型看到的历史
       ├─ projection     → 当前 Turn / inbox / preset 状态
       └─ persistence    → 重启后重新打开
仓库硬规则：凡是进入模型请求的内容，都必须能从 Session log 重建。新增模型可见输入时，必须设计对应的 Session event 或纯投影机制。

持久化 Provider 负责物理格式和读写所有权；当前 JSONL generation 使用版本命名。恢复时读取支持的 generation、执行必要的相邻迁移，然后在逻辑事件上重建 live Agent。

12 · 关键边界速查

概念对前者后者判断方式
Profile / Preset决定整个进程启动什么应用决定一个 Session 使用什么 Agent 组合影响所有 Session，还是只影响选中它的 Session？
Session / Agent耐久事件与身份当前内存执行者进程退出后它是否仍存在？

Scope / Isolate共享 Registry 内的数据可见性同名 Service 的实例路由要另一组记录，还是另一份实例？

13 · 现实应用：追踪“PTC 会话调用 bash”

用下面的判断链阅读真实代码或配置：

  1. 应用从哪里来？Web Profile 叠加 base 与 web-app bundles，App Boot 挂载 Host 插件树。
  2. 公共能力在哪里？Host 上已有 LLM、ToolsService、Shell/Sandbox、Session persistence 和 Agent Factory。
  3. 会话选了什么？Session 记录 PTC preset；Agent 创建时加入当前 PTC standing generation。
  4. bash 为什么可见？PTC composition 向共享 ToolsService 的 PTC scope layer 注册 bash；Agent 的 scope parent 指向 PTC。
  5. bash 用哪个执行器？它消费 host shell/sandbox seam；当前 PTC 配置没有私有 terminals/fs realm。
  6. 调用怎样运行？模型收到 bash schema，返回 tool call，ToolsService 经过 guarded pipeline 调用 handler。
  7. 怎样恢复？tool/call、tool/result 和 assistant settlement 写入 Session log；新 Agent 可从相同事实继续。
反例判断：“为了让 minimal 只看到 persistent-bash，应 isolate('tools')。”当前设计不这样做。它共享 ToolsService，用 scope 分层工具；只对确实需要另一实例的 terminals 使用 isolate。

14 · 费曼验收

一分钟解释

不用“依赖注入”“事件溯源”等术语，向同事解释 DeepSeek Harness 怎样从启动配置变成一个能持续对话和调用工具的应用。

参考答案与回看节点

Profile 选择并叠加若干 Bundle，启动器把最终配置交给 Cordis，Cordis 逐个安装插件。Harness 插件提供模型、工具、存储等能力。创建会话时选择一种 preset，正在运行的 Agent 获得相应提示词和工具。每次用户输入由 Agent 循环请求模型、执行工具并继续请求，发生过的关键事实写入 Session，所以重启后可以恢复。回看：学习地图、启动、一次请求。

迁移题

要让某些 Session 使用 SSH 文件系统和 SSH 子进程，但其他 Session 仍使用本机执行世界。你首先考虑 Scope 还是 isolate？为什么？

参考答案与回看节点

先考虑对应 FS/Subprocess/Sandbox 服务的独立 Provider realm，也就是 isolate，因为问题是同名有状态能力应连接不同实现。随后仍可能用 preset scope 决定哪些工具和提示词对这些 Agent 可见。Scope 不能自动替换 ctx.fs 或 ctx.subprocess。回看：Scope 与 Isolate。

辨认错误说法

“Session 选择 PTC 后，Agent Context 的 scope key 就变成 K_ptc，所以它和其他 PTC Agent 无法区分。”这句话哪里错？

参考答案与回看节点

Agent 保留自己的 key，例如 K_A；系统建立 K_A → K_ptc 的父关系。Preset 共享注册在 K_ptc，Agent 独有注册可放在 K_A，因此既能继承 PTC，又能保持每 Agent 身份与生命周期。回看：Scope。

架构定位题

一个新工具包定义 schema 和 handler，并调用现有 ctx.fs。它在 FS seam 中扮演什么角色？它自身又向什么地方贡献内容？

参考答案与回看节点

它是 FS seam 的 Consumer，因为它调用既有 FS Definition；同时它向 ToolsService 这个 Registry 注册一条 tool contribution。不要把“工具”误判为新的 FS Provider。回看：Capability Seam、注册中心。

恢复题

为什么只保存最终 messages 数组不足以完整恢复 Harness 会话？

参考答案与回看节点

系统还需要工具 call/result 配对、Turn/Step 边界、请求 header/context、失败或中断结算、preset 选择等事实，才能准确重建模型历史、当前状态和诊断信息。Session event log 才是权威事实，messages 是其投影之一。回看：日志与恢复。
